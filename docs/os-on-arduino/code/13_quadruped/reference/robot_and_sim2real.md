# arduino_os_quad_robot — 機体仕様と sim2real 設計

STS3215 サーボ 8 個で動く約 1 kg の四足ロボットを、mjlab(MuJoCo-Warp) + rsl_rl PPO で
歩かせ、**IMU 無しの Arduino Uno R4 WiFi 上で回す**ための設計メモ。
数値はすべてこのリポジトリのスクリプトで再現できる実測値で、推定値には「推定」と書いてある。

## 1. 機体

SolidWorks から書き出した `urdf/arduino_os_quad_robot.urdf` から計算した値
(`scripts/normalize_urdf.py` と `scripts/build_mjcf.py` が同じ数値を使う)。

| 項目 | 値 |
|---|---|
| 構成 | 4 脚 × 2 自由度 = **8 DoF、全関節が矢状面ピッチ**(股・膝)。外転(abduction)なし |
| 総質量 | **0.9249 kg**(胴 0.246 / STS3215 × 8 = 0.440 / 大腿 × 4 = 0.161 / 足ブラケット × 4 = 0.078)<br>2026-08-22 の CAD 改訂で 1.0378 kg から 11 % 軽量化。旧機体は `_backup_v1_2026-08-22/` |
| 胴 | 0.25 × 0.11 × 0.05 m |
| ホイールベース / トレッド | 0.150 m / 0.201 m(home 姿勢の足先間) |
| 脚 | 大腿(股→膝) 0.100 m、下腿(膝→足先) 0.117 m |
| 立位高さ | 脚を伸ばして **0.188 m**、home 姿勢で **0.110 m** |
| 関節可動域 | URDF 上 ±2 rad(実機のホーン可動域・配線は未検証) |

### 前後左右の定義

URDF の股関節は x = +0.060 と x = -0.090 に配置されている(base_link 原点は幾何中心ではない)。
**+X を前**とし、ROS 慣習(+Y = 左)に合わせて次のように命名した:

| CAD 上の名前 | 股関節位置 (x, y) | 正規化後 |
|---|---|---|
| `Assem130_6` | (+0.060, −0.052) | **FR** 右前 |
| `Assem130_right_5` | (+0.060, +0.052) | **FL** 左前 |
| `Assem130_5` | (−0.090, −0.052) | **RR** 右後 |
| `Assem130_right_6` | (−0.090, +0.052) | **RL** 左後 |

## 2. URDF の正規化(なぜ必要だったか)

CAD 書き出しの URDF はそのままでは使えない。理由は 2 つ。

1. **名前がアセンブリのインスタンス名**
   (2026-08 以降は `Assem130_right_6__bracket_outline_1`、それ以前は
   `Assem130_right_6__bracket_step_1__bracket_1_step_1`)。どの脚かが名前から分からず、
   報酬の正規表現もサーボ ID 表も全部変換表を持つ羽目になる。
2. **軸の符号が左右で不揃い**。股関節軸は左右で鏡像(y<0 側が world `+Y`、y>0 側が `-Y`)
   なのに、**膝関節軸は 4 本とも world `+Y`**。この状態で 4 脚に同じ角度を入れると
   2 本が逆に曲がる。実測: `hip=-0.3, knee=+0.6` を全脚に入れると **55.9° 傾く**。

`arduino_os_quad_robot/scripts/normalize_urdf.py` が両方を書き換えて
`urdf/arduino_os_quad_robot_rl.urdf` を生成する(CAD 書き出し側は一切編集しない)。
軸の反転は関節角の符号反転とちょうど打ち消し合うので、**同じ機械を記述したまま**である。

正規化後の規約(4 脚とも同一。トロットが位相差だけで書ける):

* `<leg>_hip_joint` : 軸 = world +Y。**正 = 足先が後ろ(−X)へ振れる**
* `<leg>_knee_joint`: 軸 = world +Y。**正 = 足先が後ろ(−X)へ振れる**

検証: 正規化後に `hip=+0.3` を 4 脚に入れると足先が全脚 `Δ=(-0.060, 0, +0.012)` で一致する。

実機のサーボ正転方向はこれとは独立の校正定数で、`deploy/arduino_quad/arduino_quad.ino` の
`JOINTS[]` の `sign` で吸収する(実測で決めること。手順は同ファイル末尾の BRING-UP)。

## 3. アクチュエータモデル(ここが sim2real の本体)

サーボは **Feetech STS3215 / ST3215 の 12 V 版**(1:345 ギヤ、4096 counts/回転)。
URDF の `<limit effort="2.942" velocity="4.717">` はこの版の
**ストールトルク 30 kgf·cm = 2.942 N·m** と **無負荷回転数 45 rpm = 4.717 rad/s** に一致する。
連続定格は 10 kgf·cm = **0.98 N·m**、ストール電流 2.7 A、アイドル 180 mA。

> 7.4 V 版 STS3215(C001)は別物で、ストール 19.5 kgf·cm = 1.91 N·m。
> **実機がそちらなら本書のトルク値は 54% 過大**で、アセットを作り直す必要がある。

### トルク-速度直線を受動粘性として入れる

DC モータの出せるトルクはストールから無負荷速度までほぼ直線で落ちる。
専用のアクチュエータ型を使わず、その傾きを**関節の受動粘性**として MJCF に入れている:

```
b_backemf = τ_stall / ω_noload = 2.942 / 4.717 = 0.6237 N·m·s/rad
```

こうすると、飽和する位置指令を与えたときの自走速度がちょうど無負荷回転数になる。
**実測 4.72 rad/s(データシート 4.717)**。これを入れないと、sim の脚は 45 rpm のサーボでは
到底出せない速さで振れてしまう ─ サーボロボットの sim2real が失敗する定番の原因。

### システム同定が必要なパラメータ(推定値)

実機データが取れたら真っ先に詰めるべき順。学習時はいずれも広くランダマイズしている
(`mjlab_overlay/arduino_os_quad_robot/env_cfgs.py` の events)。

| パラメータ | 現在値 | 根拠 | 学習時のランダマイズ |
|---|---|---|---|
| `stiffness` (サーボ内部 P) | 20 N·m/rad | **推定**: 0.15 rad の偏差でストールトルク相当 | ×0.6 〜 ×1.6 |
| `armature` (換算ロータ慣性) | 0.002 kg·m² | **推定**: ロータ 2e-8 × 345² | ×0.5 〜 ×2.0 |
| `frictionloss` (ギヤ乾性摩擦) | 0.01 N·m | **推定** | 絶対値 0 〜 0.04 |
| `viscous_damping` (逆起電力) | 0.624 N·m·s/rad | **データシート比** | ×0.7 〜 ×1.4 |
| `effort_limit` | 2.942 N·m | データシート(ストール) | ×0.7 〜 ×1.0 |
| 指令遅延 | 5〜20 ms | バス往復 + 推論 | 1〜4 物理ステップ |

同定のやり方: 脚を宙に浮かせてステップ指令を入れ、位置応答の立ち上がりと行き過ぎから
`stiffness`/`armature` を、低速での動き出しの引っかかりから `frictionloss` を合わせる。

## 4. 衝突と足先

足の接地は**ブラケット先端の 13 × 12 mm の面**で起きる。メッシュから測った接触パッチの重心は
足リンク座標で `(-0.0899, 0.002, 0.0744)`(4 脚で同一。メッシュを共有しているため)。
ここに **半径 8 mm の球** `FL_toe` / `FR_toe` / `RL_toe` / `RR_toe` を置き、
学習ではこの 4 球**だけ**を衝突させる(`disable_other_geoms=True`)。

* 自己干渉は hip ±1.6 / knee ±2.0 rad の全格子で走査済み。**最小離隔 23 mm** で干渉なし。
  よって自己衝突を有効にする必要がない(隣接リンクは固定結合なので距離 0 になるため、
  関節軸まわり 35 mm を除外して評価している)。
* 摩擦は 0.7(ゴム脚を想定)。学習では 0.4〜1.1 でランダマイズする。
  **0.4 は「素の樹脂/アルミのブラケット端が硬い床に乗っている」場合の値**で、
  そこでしか歩けない方策を作らないための下限。実機はゴムを貼るべき。

## 5. IMU が無いことの帰結

実機は Arduino Uno R4 WiFi + STS3215 だけで、慣性センサが無い。したがって
**actor の観測から `base_ang_vel`(ジャイロ)と `projected_gravity` を外してある**。
sim でこれらを使った方策は実機で動かしようがない。

| | 中身 | 次元 |
|---|---|---|
| **actor**(実機で再現できるものだけ) | 指令 3 + 歩容位相 2 + 関節角 8 + 関節速度 8 + 前回 action 8 = 29、**履歴 3 段** | **87** |
| **critic**(学習時のみ。特権情報) | 上記 + 胴角速度・重力方向・胴並進速度・足高さ・接地・接地力 | 62 |

非対称 actor-critic なので critic 側の特権情報はタダである。
actor は履歴 3 段から接地や外乱を関節の動きだけで読む必要がある。

観測ノイズは機体に合わせて振り直した(上流の値は Go2 用):

* 関節速度 ±0.3 rad/s(上流 ±1.5 は無負荷 4.717 rad/s のサーボには 32% にあたり過大)
* 関節角 ±0.02 rad(12 bit で分解能 0.0015 rad、バックラッシュ 1° 程度を見込む)
* エンコーダゼロ点ずれ ±0.03 rad(サーボの中点校正誤差)

## 6. Arduino Uno R4 WiFi の制約 → 方策サイズ

RA4M1 は 48 MHz Cortex-M4、Flash 256 KB、RAM 32 KB。
上流既定の actor `(512, 256, 128)` は約 19 万パラメータ = float32 で **750 KB** なので載らない。
**学習後に小さくすることはできない**ので、最初からこのサイズで学習する:

```
actor  87 -> 96 -> 64 -> 8   (ELU)
パラメータ 15,176 個 = float32 で 59.3 KB
推論あたり 15,008 MAC → 50 Hz で 0.75 MMAC/s
```

critic は学習機の上にしか無いので `(256, 128)` のまま。

## 7. 歩容チューニング(実測に基づく修正)

**v1(素の四足レシピ + 軽い歩容シェーピング)は失敗した。** `scripts/quad_gait_report.sh` の実測:

```
tracking   vx = +0.126 m/s (cmd +0.150)
posture    base height 0.141 m   tilt 1.3 deg
per-foot       FR      FL      RR      RL
  duty       0.69    0.53    0.66    0.48
  swing h  -0.002  -0.002   0.002   0.002   m   <- 足が 2 mm しか上がらない
  steps/s    4.36    3.68    1.88    3.84       <- 意図の 0.6 s 周期の 2.6 倍
  joint speed max 4.68 rad/s  (無負荷の 99%)    <- サーボ限界に張り付き
  joint torque max 2.83 Nm    (ストールの 96%)
```

トロット(2 脚接地 65%)にはなっていたが、**足を 2 mm しか上げずサーボを限界で振り回す
高周波の擦り足**だった。速度追従も姿勢も良いので報酬だけ見ると成功に見えるが、
実機では絶対に再現しない(サーボが追従できず、発熱し、電池が落ちる)。

原因は「そうしない理由」が報酬に無かったこと。v2 で以下を追加・変更した:

| 報酬 | v1 | v2 | 狙い |
|---|---|---|---|
| `feet_swing_height` | なし | **−3.0**(目標 0.035 m) | 着地時に遊脚のピーク高さを評価。`foot_clearance` は `|z−目標|×足速度` なので、床すれすれをゆっくり撫でると罰が効かない |
| `foot_clearance` | −2.0 | **−6.0** | 同上を補強 |
| `foot_gait` | 1.5 | **3.0** | 0.6 s のケイデンスに固定する |
| `feet_air_time` | 1.5 (閾値 0.15) | **2.5**(閾値 = 周期/2 = 0.3) | 閾値は目標滞空時間と報酬上限を兼ねる |
| `action_rate_l2` | −0.1 | **−0.3** | 50 Hz のチャタリング |
| `joint_vel_l2` | なし | **−0.01** | サーボ速度限界に張り付かせない |
| `joint_torques_l2` | なし | **−0.005** | 連続定格 0.98 N·m を意識させる |

**v2 はサーボ余裕の問題は直したが、今度は止まってしまった。** 実測(iter 400、指令 0.10 m/s):

```
tracking   vx = -0.002 m/s (cmd +0.100)      <- その場足踏み
joint speed max 1.55 rad/s (無負荷の 33%)     <- サーボ余裕は解決
joint torque max 1.39 Nm   (ストールの 47%)
```

原因は歩容報酬ではなく **`track_linear_velocity` の std** だった。上流は
std = 0.5 に対し指令上限 2.0 m/s、つまり **std は最大指令の 1/4**。ここでは std = 0.12 に
対し上限 0.25 m/s(比 0.48)としていたため、

```
exp(-(0.05)^2 / (0.12)^2) = 0.84
```

= カリキュラム初期の小さい指令なら**完全に静止していても追従報酬の 8 割が貰える**。
その一方でサーボ保護の罰は動くと必ず掛かるので、「止まる」が最適解になっていた。
v3 で上流と同じ比率に直した:

```python
std_lin = 0.25 * CMD_LIN_X[1]   # 0.062
std_ang = 0.7  * CMD_ANG_Z[1]   # 0.42
```

教訓として一般化するなら、**追従報酬の std は指令レンジと一緒にスケールさせること**。
報酬の絶対値だけ見ていると「追従できている」ように見えてしまう
(v2 は静止したまま `track_linear_velocity` = 1.5 / 2.0 を稼いでいた)。
`scripts/quad_gait_report.sh` が実速度を直接測るのはこのため。

### v3 の失敗と、その裏にあったバグ

std を直しても歩かなかった。iter 1100 の実測:

```
tracking   vx = -0.005 m/s (cmd +0.100)
関節振幅   標準偏差 0.02〜0.07 rad (1〜4°)   <- 脚がほぼ固まっている
遊脚高さ   5 mm、接地デューティ 0.99/0.10/0.83/0.37
```

報酬の内訳を見ると `foot_gait` 1.63 > `pose` 0.87 > `track_ang` 0.63 >
`track_lin` 0.59。**`foot_gait` が最大の収入源**になっていた。この項は
「クロックが期待する接地状態と実接地の一致率」なので、その場で微振動して足が
正しいタイミングで浮けばほぼ満額もらえる。ケイデンス固定のため 0.5 → 3.0 に
上げたのが裏目だった。

さらにその下に本当のバグがあった。**`ContactSensor` のスロット順は、config に
書いた順ではなくモデル順**である。`ContactSensorCfg.primary` の `pattern` は
`Entity.find_geoms()` で解決され、これは MJCF に現れる順で返す。この機体では
CAD 書き出しの関節順に従って **`RR, FR, FL, RL`**。

`feet_gait` の `offset` は位置引数なので、`(FR, FL, RR, RL)` のつもりで
`[0, 0.5, 0.5, 0]` と書いた設定は、実際には `RR:0, FR:0.5, FL:0.5, RL:0`
= **後脚ペアと前脚ペアが揃う「バウンド」**を要求していた。エラーは何も出ない。
1 kg・45 rpm サーボの四足にできない歩容を報酬が要求し続け、方策は
「その場で立つ」に落ち着いていた、というのが v1〜v3 に共通する本当の原因。

対策:

| | v3 | v4 |
|---|---|---|
| `FOOT_ORDER` | `(FR, FL, RR, RL)`(誤) | **`(RR, FR, FL, RL)`**(モデル順) |
| `GAIT_OFFSET` | `[0, 0.5, 0.5, 0]` → バウンド | **`[0, 0.5, 0, 0.5]`** → RR+FL / FR+RL の対角トロット |
| `foot_gait` 重み | 3.0 | **0.75**(上流既定 0.5) |
| `pose` 重み | 1.0 | **0.5**(home 維持は「歩いていない状態」そのもの) |
| `track_linear_velocity` | 2.0 | **4.0** |
| `track_angular_velocity` | 1.0 | **2.0** |

`scripts/quad_smoke.sh` がスロット順を実行時にアサートするようにした。
同じ罠は `feet_swing_height` / `feet_slip` にもあり得たが、こちらは
`SceneEntityCfg` が `preserve_order=False` で site_ids をソートして返すため、
結果的にセンサ順と一致していた(確認済み)。

### 初期姿勢は主因ではなかった

「脚が伸び切っているのでは」という疑いを実測で潰した:

| 姿勢 | 股-足先 | 最大伸展比 | 膝内角 | 足先ヤコビアンの条件数 |
|---|---|---|---|---|
| q = 0 | 0.205 m | 99% | 176° | **76.2**(ほぼ特異) |
| **home (base 0.14)** | 0.156 m | **76%** | **99°** | **3.5** |
| base 0.12 | 0.136 m | 66% | 82° | 2.8 |

home は伸び切りではなく、Go2 (0.32/0.426 = 75%) と同じ比率。ただし深くすると
条件数が改善するので、`$ARDUINO_QUAD_HOME_HEIGHT` で 0.10〜0.14 を切り替えて
A/B できるようにしてある(IK 解の表を robot_cfg.py に同梱)。

### 起き上がり(ArduinoQuad-Recovery)は IMU 無しでは成立しなかった

3000 iter 学習後、768 試行の実測:

```
overall success:   1.0 %   (8 / 768)     成功 = 最終傾き < 25° かつ base > 0.12 m
  うつ伏せ・ほぼ正立から   90 試行   0.0%   最終傾き 100°  <- 自分から横倒しになる
  横倒しから              212 試行   1.4%   最終傾き  86°
  仰向けから              466 試行   1.1%   最終傾き  90°
最終 base 高さ 平均 0.099 m (立位 0.140)
```

学習曲線も報酬 −40 → −14 で頭打ち。胴を水平(傾き 13°)にはできるが、
base 0.057 m から立ち上がれない。

これは報酬調整で解ける類ではないと考えている。**方策は自分の姿勢を観測できない**
(IMU が無いので actor には関節角・関節速度・その履歴しか無い)。倒れた状態から
どちらへ押せばよいかは、接触配置から間接的に推定するしかなく、外転関節ゼロの
8 DoF ではロール方向の権限もほとんど無い。IMU を載せる価値が最も高いのはここ。

### 決定打: RL を使わずに「歩けるのか」を測る

歩容修正を重ねても前進しないので、報酬をいじるのをやめて
**RL 抜きの手書きトロット**を MJCF に直接流した
(`arduino_os_quad_robot/scripts/openloop_trot.py`)。脚ごとに足先の
デカルト軌道(接地相は後方へ、遊脚相は前方へ持ち上げ)を数値 IK で
(hip, knee) に落とし、MJCF の `<position>` アクチュエータに 50 Hz で書く。
つまりストールトルク・逆起電力粘性・換算慣性を含む、学習と同じサーボモデルを通る。

```
 stride  height   lift  period |  vx[m/s] | tau_max tau_p99 tau_rms | qd_p99 qd_rms
  0.080   0.140  0.030    0.50 |    0.138 |    2.94    2.94    1.64 |   4.98   2.48
  0.060   0.140  0.030    0.50 |    0.114 |    2.94    2.94    1.48 |   4.69   2.24
  0.060   0.140  0.020    0.70 |    0.086 |    2.43    2.01    0.89 |   2.84   1.32
  0.040   0.140  0.020    0.70 |    0.048 |    2.39    1.89    0.76 |   2.54   1.13
```

(初出の表は「最終ステップのトルク」を最大値として載せていた。走行中の最大を
取るよう直した結果が上記。1.30 Nm に見えていた設定は実際には 2.43 Nm 使う。)

結論は 2 つ。

1. **この機体は歩ける。** モデル・接触・アクチュエータに致命的な問題は無い。
2. **到達可能な速度は 0.05〜0.14 m/s**。ただし上端はストールトルクに張り付いており、
   **サーボ包絡線の内側**に収まる帯域は 0.05〜0.09 m/s。

ところがタスクの指令レンジは **最大 0.25 m/s** だった。つまり指令分布の大半が
物理的に到達不可能で、そこでは何をしても追従報酬が伸びない。「止まる」が
安全解になるのは当然だった。指令レンジを実測に合わせて
`lin_vel_x = (-0.05, 0.12)` / `ang_vel_z = (-0.4, 0.4)`、追従 std もそれに比例させ
(0.25 × 0.12 = 0.03)、遊脚高さ目標も飽和しない 0.025 m に下げた。

**教訓**: 指令レンジは「こうだったらいいな」ではなく、**開ループで測った到達可能域**
から決めること。この 1 本のスクリプトを最初に走らせていれば、
報酬デバッグを何周もせずに済んだ。

### 指令レンジを直しても歩かず、正味変位で測って正体が分かった

指令レンジを実測に合わせた v5(2500 iter)でも前進しなかった。ただし学習ログの
`error_vel_xy` は 0.12 で、指令の大きさ(平均 0.04)の 3 倍。「静止」では説明が付かない。
そこで**平均瞬時速度ではなく正味変位**を測った:

```
cmd vx=0.12, 6 秒, 64 env
  正味前進変位   : -0.014 m  ->  -0.002 m/s      <- 実質ゼロ
  body 座標の vx : 平均 -0.002, 標準偏差 0.107   <- p5 -0.18 / p95 +0.13
  body 座標の vy : 平均 +0.002, 標準偏差 0.027
```

**その場で前後に激しく揺れていた。** 追従報酬は指令速度を中心とした鋭いガウシアン
(std 0.03)なので、揺れの速度が指令値を通過する瞬間ごとに満額が入る。平均すれば
そこそこの追従報酬になり、ログ上は「部分的に追従」に見える。**瞬時速度で追従報酬を
出す設計に共通する穴**で、Go2 のように指令速度を余裕で出せる機体では実質的な
最適解が本物の歩行になるので表面化しないが、トルク限界ぎりぎりのこの機体では
「揺れる」方が安い。

対策(`rewards.py` に追加):

* `track_lin_vel_filtered`(重み 4.0) — **0.6 秒の一次遅れで平滑化した**base 速度を
  指令と比較する。平均ゼロの揺れは平滑化するとゼロになり 1 円も入らない。実際に
  移動していれば従来どおり満額。
* `base_vel_oscillation_l2`(重み −2.0) — 瞬時速度と平滑化速度の差の二乗。揺れを
  「無報酬」から「有害」に格上げする。
* 従来の瞬時追従は重み 4.0 → **0.5** に落として残す(「とりあえず正しい向きに動く」
  勾配としては有用なため)。
* 揺れを塞ぐと次は「凍る」に落ちるので、`alive` 0.5 → 0.1、`pose` 0.5 → 0.3 と
  静止の実入りも下げた。

いずれも `ManagerTermBase` 相当のクラス実装で、`reset(env_ids)` フックで
エピソード境界のフィルタ状態を落としている(状態を持つ報酬でこれを忘れると、
前のエピソードの速度が次に漏れる)。

### v6: 初めて歩いた。ただし実機には出せない

平滑化追従に替えた v6(2500 iter)で前進が成立した:

```
cmd 0.05 -> vx +0.049 m/s   正味前進 +0.252 m / 6 s
cmd 0.12 -> vx +0.115 m/s   正味前進 +0.175 m / 6 s
```

一方で 3 つの問題が残った(すべて `scripts/quad_gait_report.sh` の実測):

| 症状 | 実測 | 問題 |
|---|---|---|
| 左後脚が一度も接地しない | RL デューティ **0.00** | 3 本足歩行。指令 0 に対しヨーが **+0.44 rad/s** に流れる |
| サーボが限界に張り付く | 関節速度 max **4.99 rad/s (無負荷の 106%)**、トルク max **2.93 Nm (ストールの 100%)**、rms トルク 0.75(連続定格 0.98) | 実機では追従できず発熱する |
| ケイデンスが速すぎる | 4.0〜4.9 歩/秒(意図は 1.67) | 遊脚高さも 8 mm (目標 22 mm) |

原因は保護ペナルティの弱さ。`joint_vel_l2` −0.01 / `joint_torques_l2` −0.005 では、
追従報酬 3.0 に対して合計 −0.02 しか効かない。かといって一律 L2 を大きくすると
普通の歩容まで潰れる。

そこで **連続定格を超えた分だけ**を罰する形に変えた(`rewards.py`):

```python
joint_torque_excess(limit=RATED_TORQUE)        # 0.98 Nm 超過分の二乗和、重み -2.0
joint_speed_excess(limit=0.6*NO_LOAD_SPEED)    # 2.83 rad/s 超過分の二乗和、重み -0.5
```

サーボの包絡線の内側に収まっている限り**コストはゼロ**で、限界に張り付くと大きく罰する。
熱モデルが無いシミュレーションで、ギヤを焼かない歩容を選ばせる唯一の仕掛けでもある。
あわせて `foot_gait` 0.75 → 1.5(4 本とも使わせる)、`track_angular_velocity` 2.0 → 3.0
(まっすぐ歩かないコストを上げる)。

### v7/v8 が凍った原因は保護ペナルティではなかった

v7 で 4 つ同時に変えたのが失敗だった。犯人は **`track_angular_velocity` 2.0 → 3.0**。
ヨー指令は 0 中心なので、**回らない = 静止しているだけでこの項が満額入る**。
`foot_gait` 0.75 → 1.5 も同じ方向に効く。静止時の収入が v6 の約 1.4 から
v8 の約 2.5 に上がり、歩く動機が消えていた。

サーボ超過ペナルティは無罪だった。v8 の実測トルクは最大 0.75 Nm で、
しきい値 2.2 Nm に届かず**発火すらしていない**。

v6 の重みに戻した v9a は再び歩き、サーボ余裕も v6 より良くなった:

```
        v6                      v9a
cmd 0.09 -> vx 0.115      cmd 0.09 -> vx 0.084
p99 torque 2.63 Nm        p99 torque 1.71 Nm   (参照トロットの 2.01 より内側)
p99 speed  3.37 rad/s     p99 speed  2.42 rad/s
max speed  4.99 (106%)    max speed  4.26 (90%)
```

**教訓**: 失敗の原因を探すときに複数箇所を同時に変えない。
v6 は歩いていたのだから、そこから 1 つずつ変えるべきだった。

### 参照軌道による誘導(v10)は効かなかった

開ループで検証済みのトロット関節軌道を `(位相 × ストライド × 8関節)` の表に焼き
(`make_trot_reference.py`)、重み 2.0 → 0.7 → 0 と減衰させながら誘導した。結果:

| | v9a(誘導なし) | v10(誘導あり) |
|---|---|---|
| cmd 0.09 の vx | 0.084 | 0.092 |
| p99 トルク | **1.71 Nm** | 2.32 Nm |
| p99 関節速度 | **2.42 rad/s** | 3.07 rad/s |
| 最大関節速度 | 4.26 (無負荷の 90%) | 5.05 (**107%**) |
| 引きずり脚 | あり | あり |
| ヨー流れ | 0.35 rad/s | 0.47 rad/s |

前進速度は同等だが、**減衰後により攻撃的な歩容へ戻り**、引きずり脚も直らなかった。
「あとで自由に離れてよい軌道」へ誘導しても、この機体では何も残らない。
実装は `$ARDUINO_QUAD_TROT_GUIDE=1` で opt-in として残してある。

### 全バージョン共通で残った「引きずり脚」

v6 / v9a / v10 のすべてで**左後脚の接地デューティが 0.00**。3 本足で歩き、
その非対称でヨーが 0.35〜0.47 rad/s 流れる。既存の報酬はこれに何も言わない:

* `feet_air_time` は脚方向に **min** を取る → ずっと浮いている脚は見えない
* `foot_gait` は脚方向に **平均** → 3 本が正しければ 1 本の異常が薄まる

`foot_air_time_excess`(歩容周期の 2 倍を超えて浮いている時間を**線形**に罰する、
重み −1.0)を追加した。二乗にしないのは、1 エピソード丸ごと浮いた脚が
学習を不安定にするスパイクを出さないため。

### 「本当に交互か」はデューティでは分からない

v12 の接地デューティは RR 0.50 / FR 0.63 / FL 0.61 / RL 0.49 と揃って見えたが、
**位相**を測ると別の姿が出た(`scripts/quad_eval_one.py` が毎回これを出す):

```
接地位相 (RR 基準、0=同相 / 0.5=逆相)
        RR      FR      FL      RL
平均   0.00    0.49    0.39    0.51
ばら   0.00    0.03    0.44    0.06     <- FL だけ位相が固定されていない
理想   0.00    0.50    0.00    0.50

2脚支持の内訳: 対角 66% / 同側 0% / 前後 7%
歩容周波数 3.43 Hz = 周期 0.292 s   (与えていたクロックは 0.600 s)
```

デューティが 0.5 前後でも、位相がランダムなら交互ではない。**ロボットは
クロックの 2 倍の周波数で歩いていた**ので `foot_gait` は隔サイクルでしか一致せず、
位相を固定する力になっていなかった。

歩容周波数はおよそ 1/sqrt(脚長) でスケールする。Go2 は脚 0.4 m で 2-3 Hz、
この機体は脚 0.19 m なので **3-4 Hz が自然**で、0.6 s (1.67 Hz) は遅すぎた。
`GAIT_PERIOD` の既定を **0.30 s** にし、`$ARDUINO_QUAD_GAIT_PERIOD` で振れるようにした。

## 9. 別プロジェクト(大型四脚の RL)から持ち込んだ知見

別プロジェクトに、同じ mjlab で **30 kg・12 DoF の
四足**を歩行 1.0 m/s・走行 1.5 m/s まで持っていった記録がある
（そちらの歩行の引き継ぎ資料）。機体は違うが、効いた知見は 3 つ。

1. **⭐ 足クリアランスは運動学的天井**。あちらは足上げ報酬を **16 倍**にして
   scratch 2000 iter 学習しても foot_lift が 2.5 → 3.0 cm しか伸びず、
   「報酬/探索の問題ではなく **スタンス高と脚形状のトロット可動域限界**」と結論している。
   上げたいなら **base を下げて膝可動域を稼ぐ**。
   → こちらの遊脚高さ 6-11 mm(目標 22 mm)も同じ性質と見て、報酬ではなく
   `$ARDUINO_QUAD_HOME_HEIGHT` を振る A/B に切り替えた。
2. **`foot_gait` を強くすると gait 遷移を阻害する**。あちらは 1.5 m/s の走りを
   出す際、対角トロット強制がギャロップへの移行を妨げるため 0.5 まで落として突破した。
   → こちらで `foot_gait` 3.0 が静止を招いた話と同じ方向。強い gait 拘束は害。
3. **トルクは絞ってもタダ**。歩行中の実トルクを測って effort を 24 → 18 Nm に絞ったら
   最大が定格内に収まったうえ追従も 0.82 → 0.83 と改善した。
   → 実機狙いなら effort を絞る価値がある(こちらは未適用、次の候補)。

あちらとの構成差も記録しておく: あちらは `unitree_rl_mjlab` を直接 fork して
`src/` にファイルを置いているが、こちらは overlay(`mjlab_overlay/` を setup.sh が
コピー)方式で上流を fork しない。報酬はあちらが **Go2 レシピほぼそのまま**で歩いたのに対し、
こちらは 8 DoF・外転なし・45 rpm サーボという厳しい条件のため独自項が増えている。

### 前後の向き — 実機の組み立てに合わせて 180 度回した

膝の曲がり向きが実機と逆だと指摘を受けて調べ直した。足ブラケットは S 字で、
リンク原点側にホーン取付面、先端に接地ノブがある。部品としては正しく付いていたが、
**膝の頂点がどちらを向くか**が実機と食い違っていた。

膝頂点を実機どおりにすると、開ループの実力が半減した:

```
                       vx        胴の傾き(最大)
CAD の +X 側を先頭に   0.089 m/s   21.5 度
反対側を先頭に         0.156 m/s    8.3 度
```

つまり **CAD の +X 端（中実部のある側）は尾**だった。`normalize_urdf.py` に
base 直下を Rz(180 度) 回す段を入れ、URDF の時点で「進むべき端が +X」になるようにした。
指令を反転させる方式にしなかったのは、下流の規約(タスクの前方 = base +X、
ROS の +Y = 左)をすべて素直に保てるため。脚名も回転後の座標で付け直している
(前脚 x=+0.090、後脚 x=-0.060)。

ここで自分の初期の説明が誤っていたことも判明した。「膝反転と前後反転は同じ機体」と
書いたが、**股サーボのホーン offset が 4 本とも同じ向きに 11.9 mm** ついているので
機体は前後対称ではない。実際に開ループの実力が倍違った。

この付け替えで接触センサのスロット順が `RR,FR,FL,RL` → `FL,RL,RR,FR` に変わり、
`quad_smoke.sh` のアサートが検出した。同じ罠を 2 回踏まずに済んだ。

### 転倒判定 60 度 → 35 度で学習の成功率が 2/8 → 2/2 に

前後反転後、学習が**シードの 6/8 で失敗**するようになった。失敗の型は全部同じで、
**後脚 2 本で座り込み前脚 2 本を 0.1 m 上げたまま、傾き 22 度**(接地デューティ
0.06 / 0.66)。報酬ハックではなく単純な学習失敗で、平均報酬は −4.2、`alive` はほぼゼロ。

前後反転で重心配分が前 55% から後ろ 55% に移ったことが効いていると見ている
(CoM x は +0.008、前脚 x=+0.090 / 後脚 x=-0.060)。

平地を歩く 1 kg 四足が 22 度も仰け反る必要はない(歩けたシードは 4-8 度)ので、
`fell_over` の判定を **60 度 → 35 度**に締めた。座り込みの局所解を早期に打ち切る狙いで、
新規 2 シードとも歩行が成立した。

### 最終成果

| | |
|---|---|
| 方策 | `ArduinoQuad-Robust` fine-tune(初期状態ランダム化、**ERFI なし**) |
| 前進速度 | **0.148 m/s**(= 0.59 体長/秒)、指令上限 0.15 |
| 歩容 | 対角トロット 3.33 Hz、対角支持率 0.76、最小接地デューティ 0.50 |
| 直進性 | ヨー流れ +0.00 rad/s(指令 0) |
| 姿勢 | 傾き 6.0 度、胴高 0.11 m |
| サーボ | 関節速度 p99 2.70 rad/s(無負荷の 57%)、最大 84% |
| 外乱下 | 学習相当の外乱で**生存率 100%**、4 倍で 89.8%、6 倍で 55-61% |

外乱テスト(`scripts/quad_stress.sh`: 初期状態を崩し、外乱プッシュを戻し、観測ノイズも有効、
128 env × 8 秒)。**学習時と同程度の外乱では全条件が生存率 100% になって差が付かない**ので、
プッシュを 1-8 倍に強めて破綻点を測る:

```
                        push x4     push x6
Robust のみ (ERFI なし)   89.8 %    55.5-60.9 %   <- 採用
Robust + ERFI  seed1      80.5 %      45.3 %
Robust + ERFI  seed2      90.6 %      46.1 %
頑健化なしで継続          81.2 %      47.7 %
fine-tune なし            66.4 %      34.4 %
```

読み取れること:

1. **fine-tune 自体が効く**(66 → 90 %)
2. **リセット時の状態ランダム化(Robust)が効く**(81 → 90 %)
3. **ERFI は効果が測れない**。2 シードとも ERFI なしを上回らず、x6 では明確に下。
   ただしシード間のばらつきが x4 で 10 ポイントあるので、「有害」とまでは言えない

この機体の正味トルクは連続定格の 1/3 しか出ておらず、トルク空間の摂動が
コントローラが既に吸収している範囲に埋もれている可能性がある。
60 kg でアクチュエータを限界近くで使う大型機では ERFI が効いていた。

**最初は ERFI 版を採用と報告したが、それは誤りだった。** 弱い外乱で全条件が
生存率 100% になる中、最大傾きの 1 点(12.3° 対 20.1°)を差だと誤読していた。
掃引すると順位が逆転する。**外乱テストは破綻点まで振らないと何も言えない。**

## 8. デプロイ経路と、その検証

`deploy/arduino_quad/` の構成:

| ファイル | 中身 | 検証 |
|---|---|---|
| `arduino_quad_policy.h` | 重み + 前向き計算 + 観測レイアウト定数。`scripts/export_quad_policy.sh` が生成 | **自動**: PyTorch actor と一致(1.9e-06)、生成 C を実際にコンパイルして numpy と一致(9.5e-07) |
| `quad_control.h` | 観測の組み立て・履歴・歩容クロック・action → 関節目標。純 C99 | **自動**: `scripts/check_quad_control.sh` が学習済み方策のロールアウト上で mjlab と突き合わせ(観測 4.8e-07、関節目標 1.2e-07、200 ステップ) |
| `arduino_quad.ino` | サーボバス I/O・50 Hz ループ・安全停止 | **未検証**。実機でコンパイルも実行もしていない |

sim2real で壊れるのはほぼ常にネットワークではなく**観測の作り方**(項目の順番、履歴の向き、
基準姿勢の引き方、単位)なので、そこを機械的に突き合わせられるようにしてある。
方策を再学習・再エクスポートするたびに 2 つのチェックを回すこと。

観測レイアウト(ヘッダにも同じものが書き出される):

```
[  0..  9) command    3 段 × 3   (vx, vy=0, wz)
[  9.. 15) phase      3 段 × 2   (sin, cos。|指令| < 0.1 で 0 に固定)
[ 15.. 39) joint_pos  3 段 × 8   (現在角 − home 角)
[ 39.. 63) joint_vel  3 段 × 8
[ 63.. 87) actions    3 段 × 8   (前回の生 action)
各項目とも履歴は古い順
関節順: RR_hip, RR_knee, FR_hip, FR_knee, FL_hip, FL_knee, RL_hip, RL_knee
サーボ目標 = home 角 + 0.25 × action
```

## 9. 既知の sim2real ギャップ

* **実機未検証**。このリポジトリは実機で一度も動かしていない。
* **サーボ内部制御が黒箱**。STS3215 のファームの位置ループは公開されていない。
  §3 の `stiffness`/`armature`/`frictionloss` は推定値で、同定が最優先。
* **CAD に電装が入っていない**。バッテリ・Arduino・配線の質量が URDF に無い。
  学習では base に 0〜250 g を足してランダマイズしているが、実測して入れ直すべき。
* **足裏材質**。摩擦 0.4〜1.1 でランダマイズしているが、実機の足先が何かは未確認。
* **バス帯域とループ周期**。8 サーボの読み書きが 20 ms に収まるかは実測が必要
  (`.ino` が `infer_us` / `late_us` を毎秒印字する)。歩容クロックは実時間前提なので、
  周期が狂うと歩けなくなる。
* **横移動はできない**。外転関節が無いので `lin_vel_y` は 0 に固定してある。
  旋回は左右の歩幅差で出す。
* **熱**。トルク上限はストール値で、熱モデルは無い。連続定格 0.98 N·m を
  `scripts/quad_gait_report.sh` の RMS で下回っているか毎回確認すること。
