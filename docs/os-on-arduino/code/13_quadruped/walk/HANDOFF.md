# arduino_os_quad_robot — 実機引き継ぎ  (2026-08-23)

STS3215 サーボ 8 個・質量 1.04 kg・外転関節なしの四足を歩かせる学習済み方策と、
それを実機で回すためのコード一式。**実機ではまだ一度も動かしていない。**

------------------------------------------------------------------------
## まず読む: どちらの経路で立ち上げるか

**推奨は Mac から USB で直結する経路。** Arduino を焼かずに済み、途中の値が全部
印字でき、直して試すのがキーストローク 1 回になる。Arduino スケッチは最終的な
組み込み先であって、最初にデバッグする相手ではない。

    Mac ─USB─ FeetechのUSB-TTLアダプタ ─半二重TTL─ サーボ 8 個
                    (Waveshare Serial Bus Servo Driver 等)

    pip install feetech-servo-sdk pyserial numpy
    ls /dev/tty.usb*                      # tty.usbserial-* か tty.usbmodem*

    python host/quad_host.py --port /dev/tty.usbserial-XXXX scan
    python host/quad_host.py --port ... calibrate --write-middle
    python host/quad_host.py --port ... stand
    python host/quad_host.py --port ... run --vx 0.05

------------------------------------------------------------------------
## Arduino Uno R4 WiFi に移すとき

上の Mac 経路が一通り動いてから。`arduino/` には**スケッチごとにフォルダ**が
ある(Arduino は 1 フォルダ内の .ino を全部まとめて 1 つにコンパイルするので、
2 つを同じフォルダに置くと setup() が重複してどちらも通らない):

    arduino/arduino_quad/   歩行本体 + quad_control.h + arduino_quad_policy.h
    arduino/calibrate/      ID・符号・ゼロ点の校正ウィザード

    arduino-cli core install arduino:renesas_uno
    arduino-cli lib  install SCServo
    arduino-cli compile -b arduino:renesas_uno:unor4wifi arduino/arduino_quad

**数値の中身は Mac 経路と同一**。`host/quad_policy.py` と `quad_control.h` は
どちらもシミュレータと一致することを確認してある(下の検証記録)ので、Mac で
歩いたなら方策も観測の作り方も正しい。Uno R4 で新しく増えるリスクは
**バスの配線と制御周期だけ**:

* 半二重の方向切替は R4 の Serial1(D0/D1)には無い。Mac と同じく、方向切替を
  する回路/アダプタを挟むこと。TX/RX を直結しても応答は返らない。
* サーボ電源は必ずバッテリから。R4 の 5 V からは取らない。
* `'g'` で走らせると毎秒この行が出る。**これが実機での唯一の性能証拠**:

      infer_us=... late_us=... skipped=... read_fail=...

  `skipped` は制御周期を落とした回数。歩容クロックは `step * 0.02 s` なので、
  ここが増えると位相が実時間からずれて、それだけで歩かなくなる。
  0 のままであること。`read_fail` はサーボが応答しなかった回数。

------------------------------------------------------------------------
## 電源とハードの前提

* サーボ 8 個の電源は**必ずバッテリから**。**Mac の USB からは絶対に取らない**
  (1 個あたりストール 2.7 A、アイドル 180 mA)。
* USB-TTL は**半二重の方向切替をするアダプタ**であること。ただの USB-シリアルでは
  応答が返らない。
* サーボは **1 Mbps**(工場出荷値)。50 Hz 制御にはこれが要る:
  1 回の位置読み出しが 16 バイトで、8 個ぶんが 115200 bps だと 12〜16 ms かかり
  20 ms の予算に収まらない。`scan` はボーレートを自動探索して警告する。
* 足裏にゴムかシリコンを貼ること。学習では摩擦 0.4〜1.1 でランダマイズしているが、
  素の樹脂/アルミ端は硬い床で 0.3〜0.4 しかない。

## 立ち上げ順序

1. **`scan`** — 8 個応答するか。しなければ電源・アダプタ・ID 重複を疑う。
2. **`calibrate`** — 対話式。ロボットは**吊るすか手で持つ**こと。
   1. ID と関節の対応: 1 個ずつ ±10° 振れるので、動いた関節を答える
   2. ゼロ点: **大腿(股関節軸→膝軸)が鉛直**、そのとき足先は膝の真下から 8 mm 前。
      これが `q = 0`。数度ずれてよい(学習でゼロ点 ±1.7°、関節角 ±8.6° をランダム化済み)
   3. 符号: 各関節を「足先が**後ろ**(尾側)へ振れる」向きに振って保持。カウントの
      増減で自動判定。左右で符号が食い違うのは正常(脚が鏡像に組まれているため)
   4. 範囲チェック: home ±1.2 rad が 0〜4095 に収まるか
   5. `--write-middle` を付けると、ゼロ点を EEPROM に書く(レジスタ 40 に 128)。
      MCU を焼き直しても消えず、カウントの 0/4095 をまたぐ危険も消えるので推奨
3. **`stand`** — home 姿勢へ 2 秒でランプ。ここで**4 本とも膝が後ろ(尾側)に
   引けているか目視する**。全部前に出ていたら前後の規約が学習と逆。
4. **`run --vx 0.05`** — まず吊るしたまま。毎秒印字される `late` を見る。
   これが 20 ms に近づいていたら 50 Hz が回っていない。歩容クロックは実時間前提
   なので、周期が狂うとそもそも歩けない。
5. 問題なければ床に置いて `--vx 0.05` から。

**符号か ID を間違えると、下手に歩くのではなく暴れる。** 2〜3 度の角度誤差は
学習側のランダマイズが吸収するので、そこは神経質にならなくてよい。

## 方策の仕様(ここを取り違えると静かに壊れる)

    観測 87 次元 -> [96, 64] -> 8 出力   制御周期 0.02 s   歩容クロック 0.32 s
    元チェックポイント: model_4498.pt
    学習 run:  2026-08-23_00-49-07_v2_rb_s203
    ロバスト化: 済み — リセット姿勢/速度と関節角をランダム化した fine-tune (胴の傾き ±0.15 rad, 胴の速度 ±0.30, 関節角 ±0.15 rad, 関節速度 ±0.50 rad/s)。ベース run: 2026-08-22_23-46-09_v2_s203

関節の並び(**方策の 8 出力の順。並べ替えない**):

  0  FL_hip_joint home +1.0307 rad  scale 0.25
  1  FL_knee_joint home -1.7629 rad  scale 0.25
  2  RL_hip_joint home +1.0307 rad  scale 0.25
  3  RL_knee_joint home -1.7629 rad  scale 0.25
  4  RR_hip_joint home +1.0307 rad  scale 0.25
  5  RR_knee_joint home -1.7629 rad  scale 0.25
  6  FR_hip_joint home +1.0307 rad  scale 0.25
  7  FR_knee_joint home -1.7629 rad  scale 0.25

    サーボ目標 = home 角 + scale × action

観測ベクトルの並び(各項目が自分の履歴を持ち、**古い順**に並ぶ):

  [  0..  9)  command    3 段 × 3
  [  9.. 15)  phase      3 段 × 2
  [ 15.. 39)  joint_pos  3 段 × 8
  [ 39.. 63)  joint_vel  3 段 × 8
  [ 63.. 87)  actions    3 段 × 8

* **IMU は使っていない。** この機体には無いので、観測は関節角・関節速度・
  前回 action・指令・歩容位相だけ。胴の姿勢は方策から見えていない。
* 指令は (vx, vy, wz)。**vy は必ず 0**。外転関節が無いので横移動はできない。
* 歩容位相は `sin/cos(2π · (t mod 0.30)/0.30)`。`|指令| < 0.1` のときは 0 に固定。
  t は方策を開始してからの経過時間。

## 期待できる性能(シミュレーション)

    前進 0.148 m/s (0.59 体長/秒)   対角トロット 3.33 Hz   対角支持率 0.76
    旋回 指令 0.35 rad/s に対し実測 0.26 (73%。外転が無く歩幅差で作るため)
    サーボ 関節速度 p99 = 無負荷の 57%、正味トルク = 連続定格の 1/3
    外乱 学習相当で生存率 100%、プッシュ 4 倍で 89.8%、6 倍で 55〜61%

**遅い**のはハードの性質で、学習の失敗ではない。45 rpm のサーボに 0.19 m の脚では
0.05〜0.15 m/s が素の実力。律速はトルクではなく無負荷回転数。

## うまく行かないときに持ち帰るもの

シミュレーション側を直せるのは、実機の数字があるときだけ。次のどれかがあると
こちらでパラメータを同定して MJCF に反映し、再学習まで回せる。

1. **サーボ 1 個のステップ応答** — 机に固定して位置指令を階段状に変え、
   時刻・指令・実位置を記録したもの。これがあれば `stiffness`(サーボ内部 P)、
   `armature`(換算ロータ慣性)、`frictionloss` が決まる。**sim2real の 8 割はここ。**
2. **`run` のログ** — `late` の推移。50 Hz が回っているかの判定に要る。
3. **歩かせたときの動画** — 横から、地面が見える画角で。追従カメラだと前進が見えない。
4. 実機の質量(電装込み)。CAD には電装が入っておらず、学習では 0〜250 g を
   ランダマイズしているだけ。

## 既知の穴

* **実機で一度も動かしていない。**
* サーボ内部の制御が黒箱。`stiffness` / `armature` / `frictionloss` は推定値で、
  幅を持たせてランダマイズしてあるが実測はしていない。
* 遊脚高さ 12 mm。実床の段差には心もとない。別プロジェクトの 12 DoF 四足で
  「足上げ報酬を 16 倍にしても伸びない、スタンス高と脚形状で決まる運動学的天井」と
  結論が出ており、ここも同じ性質と見ている。伸ばすなら機体側の話。
* 転倒からの起き上がりは**できない**。IMU が無く自分の姿勢を観測できないため、
  学習しても成功率 1.0% だった。IMU を載せる価値が最も高いのはここ。
* `reference/` の md には、ここに至るまでに踏んだ失敗と原因が全部書いてある。
  実機で妙な挙動が出たら、まずそこを読むと同じ罠を二度踏まずに済む。
