# rl/cpu — GPU なしで学習する

`ArduinoQuad-Walk` / `-Robust` を、mjlab を使わずに**素の MuJoCo** で学習する
コードです。物理は CPU の `mujoco.rollout`（C++ のスレッドプール）で回し、
PPO は mjlab 版と同じ rsl-rl-lib 5.0.1 を使います。ネットワークの更新は
`--device` で CPU・GPU のどちらにも置けます。

```bash
cd docs/os-on-arduino/code/13_quadruped/rl/cpu
uv sync                                   # mujoco 3.7.0 + rsl-rl-lib 5.0.1 + torch
uv run train.py                           # Walk、2048 環境、CPU
uv run train.py --device cuda             # 物理は CPU のまま、更新だけ GPU
uv run evaluate.py --checkpoint logs/rsl_rl/arduino_quad_velocity/<run>/model_2299.pt
uv run ../../host/export_quad_policy.py \
    logs/rsl_rl/arduino_quad_velocity/<run>/model_2299.pt 出力先 --backend cpu
```

mjlab 版（`../scripts/train.sh`）はそのまま残っています。両者は同じタスクで、
チェックポイントの形式も同じなので、**どちらで学習したものもどちらで続きから
学習でき、同じエクスポータでヘッダに書き出せます**。

画面の無いサーバで `--video` を使うときは `MUJOCO_GL=egl` を付けてください。
付けないと MuJoCo が GL のコンテキストを作れず、`Renderer` の生成で落ちます。

## ファイル

| ファイル | 中身 |
|---|---|
| `task.py` | タスクの数値すべて（機体・アクチュエータ・観測・指令・報酬 26 項・終了条件・リセット・ドメインランダマイゼーション・PPO）。mjlab 版と同じ環境変数（`ARDUINO_QUAD_*`）で変えられる |
| `quad_env.py` | ベクトル化した環境（rsl_rl の `VecEnv`）。1 ステップの中身は mjlab の `ManagerBasedRlEnv.step` と同じ順序 |
| `train.py` | 学習の入口。ログは mjlab と同じ `logs/rsl_rl/arduino_quad_velocity/<日時>_<名前>/` |
| `evaluate.py` | 決まった指令で歩かせて、前進・旋回の速さ、ロール・ピッチ、転倒数を出す。`--video` で mp4 |
| `parity_check.py` | mjlab 版と同じタスクになっているかの検査（下記） |

## mjlab 版と同じであることの確認

`parity_check.py` は mjlab の Python 環境（`../scripts/setup.sh` で入るもの）で
動かします。GPU は要りません（warp の CPU バックエンドで mjlab を回します）。

```bash
source ../scripts/env.sh
cd "$ARDUINO_QUAD_UPSTREAM"
PYTHONPATH="$ARDUINO_QUAD_ROOT/rl/cpu" python "$ARDUINO_QUAD_ROOT/rl/cpu/parity_check.py" \
    --npz "$ARDUINO_QUAD_ROOT/arduino_quad_policy.npz"
```

1. **設定**: `task.py` の数値を、mjlab 側の `ArduinoQuad-Walk` / `-Robust` の
   設定オブジェクトと 1 つずつ突き合わせます（報酬の重みとパラメータ、観測の
   ノイズ、指令とカリキュラム、イベント、終了条件、アクチュエータ、遅延、PPO）。
2. **ダイナミクス**: 同じ初期状態・同じ指令・同じ行動列で両方を回し、関節角・
   胴体の高さ・方策の観測・報酬 26 項をステップごとに比べます。遅延は 5 物理
   ステップに固定し、ドメインランダマイゼーションは切ります（乱数を引かない
   ようにするため）。

2026-09-22 の実測（配布済み方策で 4 環境 × 25 ステップ、初期位置を変えて 3 回）:
関節角の差 1e-6 rad 以下、方策の観測の差 7e-5 以下、報酬は 25 項が 1e-4 以下で
一致しました（mjlab 側は float32 なので、このくらいの差は残ります）。

違いが残るのは次の 2 つです。

- `joint_acc_l2`（重み −2.5e-7）: mjlab は MuJoCo の `qacc` を使いますが、
  `rollout` は `qacc` を返さないので、最後の物理ステップの速度差 / dt で
  代用しています。
- 批評家（critic）の観測のうち足先の高さ・接地・接触力は、リセットされなかった
  環境では 1 物理ステップ古い値です（mjlab は観測の前に全環境で `forward` を
  やり直します）。方策（actor）の観測には関係しません。

## 再現している mjlab の細かい挙動

見落とすと別の MDP になってしまう点です。どれも `parity_check.py` の
ダイナミクス比較で見つけて合わせました。

- **リセット直後の 0 rad 指令**: mjlab は、どれかの環境がリセットされたステップで
  `scene.write_data_to_sim()` をもう一度呼びます。リセットで関節目標は 0 に
  クリアされるので、リセットされた環境には 0 rad（脚を伸ばした姿勢）が遅延
  バッファに積まれ、新しいエピソードの最初の 4〜7 物理ステップはこれが
  サーボに届きます。リセットされなかった環境にも、同じ目標が 1 回余分に積まれます。
- **1 物理ステップ古い値**: 報酬と終了判定が見る胴体の位置・速度・足先・接触・
  アクチュエータ力は、最後の物理ステップが始まる前の状態のものです。
- **エンコーダのゼロ点誤差**は目標角から引かれるだけで、観測には足されません
  （mjlab 1.3.0 の `joint_pos_rel` は `biased=False` が既定）。
- **足の接地・滞空時間は float32**: mjlab（warp）は物理の時刻を float32 で
  積み、その差で接地時間を足していきます。そのため、制御周期のちょうど頭で
  接地した足が「着地した瞬間」（接地時間 < 0.02 s + 1e-8）に数えられるかどうかは
  丸め方で決まり、数えられないと遊脚の最高点がリセットされずに次の着地で
  大きな罰になります（`feet_swing_height`）。これも同じ手順の float32 で再現しています。
- **押しのタイマー**はエピソードをまたいで回り続けます。mjlab がリセット時に
  引き直すのは `reset` を持つクラスのイベントだけで、押し（関数）は対象外です。

## 速さ

ノート PC（Core i9-8950HK、6 コア 12 スレッド、2018 年）での実測:

| 環境数 | 物理（24 ステップ分） | 1 iteration（PPO 更新込み、CPU） |
|---|---|---|
| 2048 | 0.78 秒 | 1.55 秒 |
| 4096 | 1.50 秒 | 3.13 秒 |

約 63,000 env-steps/s で、mjlab 版を RTX 4090 で回したとき（63,700 steps/s）と
同じくらいです。

同じノート PC で 2048 環境 × 2300 iteration を通しで回すと **68.9 分**でした
（1.80 秒/iteration）。上の表の 1.55 秒はベンチだけを測った値で、実際の学習では
ログとチェックポイントの書き出しが乗ります。

## 何 iteration で歩くようになるか

上の通し（`ARDUINO_QUAD_HOME_HEIGHT=0.11 ARDUINO_QUAD_GAIT_PERIOD=0.32`、2048 環境、
1 シード）の 100 iteration ごとのチェックポイントを、`evaluate.py` で**指令
0.09 m/s・32 環境・12 秒**ずつ再生した実測です。接地率は 4 本の足それぞれが
接地している時間の割合（最小〜最大）、対角の同期は対角 2 本が同時に接地／離地して
いる割合、滑りは接地中の足先の水平速度です。

| iteration | 前進 [m/s] | 接地率 | 対角の同期 | 滑り [mm/s] | 転倒 |
|---|---|---|---|---|---|
| 0 | 0.000 | 0.00–1.00 | 0.00 | 0 | 0 |
| 100 | — | — | — | — | 全機 |
| 200 | — | — | — | — | 全機 |
| 300 | −0.003 | 0.00–0.99 | 0.33 | 19 | 0 |
| 400 | 0.036 | 0.21–0.86 | 0.44 | 75 | 0 |
| 600 | 0.026 | 0.28–0.82 | 0.31 | 79 | 0 |
| 800 | 0.088 | 0.38–0.78 | 0.53 | 73 | 0 |
| 1000 | 0.089 | 0.38–0.78 | 0.56 | 68 | 0 |
| 1500 | 0.088 | 0.36–0.77 | 0.55 | 62 | 0 |
| 1800 | 0.092 | 0.46–0.72 | 0.65 | 45 | 0 |
| 2000 | 0.090 | 0.46–0.67 | 0.69 | 41 | 0 |
| 2299 | 0.089 | 0.47–0.68 | 0.70 | 41 | 0 |

**100〜200 iteration では全機が転びます。** まだ立っていられないので、
「転ばない」を覚えるまでの区間です。300 で転ばなくなり、400〜600 は前に出ようと
して横に流れ（このとき旋回速度が 0.36 rad/s まで出ます）、指令の速度に届くのが
800 前後です。

**速さは 1000 iteration で頭打ちですが、歩容はそこから 2300 まで良くなり続けます。**
接地率が 4 本そろい（0.38–0.78 → 0.47–0.68）、対角の同期が 0.53 → 0.70 に上がり、
滑りが 73 → 41 mm/s に減ります。1500〜1800 でひと段落良くなるのは、`trot_guidance`
（歩容を教える報酬）の重みが 1400 iteration で 0 になった直後です。前進の速さだけを
見て学習を止めると、この区間を捨てることになります。

最終チェックポイントを既定の指令セットで再生すると次のようになります
（64 環境 × 20 秒、転倒 0）。

| 指令 vx, wz | 実測 vx [m/s] | 実測 wz [rad/s] |
|---|---|---|
| 0.06, 0 | 0.058 | −0.013 |
| 0.09, 0 | 0.089 | −0.065 |
| 0.12, 0 | 0.112 | −0.042 |
| 0, 0.3 | −0.008 | 0.206 |
| 0.06, −0.3 | 0.046 | −0.225 |

## 変えていること

- `ARDUINO_QUAD_TERRAIN=rough`（凹凸地面）は、mjlab の地形生成器をそのまま
  写したものではありません。同じ 3 種類（平地 30 %・ランダムな凹凸 40 %・波 30 %、
  高さ 5〜25 mm）を環境ごとの 8 m 四方のハイトフィールドとして作ります。
- `ArduinoQuad-Flat` と `-Recovery` は移していません（歩かせるのに使うのは
  `-Walk` と、その仕上げの `-Robust` です）。
